# Account requests: pending values and recovery

Email and password values now stay locked while their request is pending. This prevents editing a different value after the API has already received the submitted value. A native disabled fieldset also locks password visibility and reset controls. Wrong-current-password errors use the actual INVALID_PASSWORD code; connection and other failures show retry guidance and retain the typed values.

Open [local email settings](http://localhost:3001/settings/email) or [local password settings](http://localhost:3001/settings/password) with the disposable frontend on 3001, API on 3200 and a signed-in demo account. Submit a new email: fields lock until the real API responds, then the current-mailbox confirmation instructions appear. For password recovery use an incorrect current password, then disconnect the API and retry: the two failures have different messages, and entered values remain.

Run `AUTH_LIVE_PROOF=1 pnpm exec playwright test tests/e2e/account-pending-live.spec.ts tests/e2e/auth-account-live.spec.ts tests/e2e/account-guards-live.spec.ts tests/e2e/logout-live.spec.ts`. All 19 scenarios pass. The new four scenarios hold real responses (email 200, wrong-password 400); only the last connection failure is deliberately injected. The pending-field assertion failed before the fix. Existing flows verify actual password updates, reset, two-mailbox email changes and deletion. No successful response is mocked. New email requests are left unconfirmed, so the seeded account address and password stay intact.
